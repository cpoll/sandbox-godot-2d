# Testing
Test methodology:
    1. Open up and pin the Debugger -> Profiler and click Autostart
    2. Run the game until the bullets hit the bottom and start despawning
    3. Observe the Frame Time after 30s.


Tests are done with 50 bullet rows and a spawn rate of 0.1seconds unless specified.

Number | Conditions | Frame Time (ms)
---
1 | Naive | 16-24
2 | Naive w/ collision layers | 15-17
3 | Above, with 25 bullet rows | 4-7
4 | queue_free disabled | constantly increasing
5 | pooling | 10-13ms
6 | collision disabled | 10-13
7 | area2d deleted | 5
8 | area2d not monitoring | 10-13
9 | spawner moves bullets | 10-13

# Test Notes

Test 2/3: Seems obvious enough that we're close to dropping frames, and the naive approach
isn't good enough. Still, 50 rows spawning every 0.1 seconds is a lot of bullets,
more than I think you see in a danmaku (I should add a bullet count).
But even 4ms seems like a long time for this.

Test 4: Commented out queue_free(). The flame graph shows a lot of time spent on 'Cull CanvasItem Tree'. I think that's
deciding which elements don't need to be rendered (should be culled). I think this increases linearly
with number of elements in the scene. Commenting out queue_free() suggests as much, as it increases
linearly (or some low order exponential) with time running. Does multimesh bypass this?

Test 5: Added pooling. Lower time, but I wonder if that's just an artifact. It also makes the bullets a bit
janky; I might not be properly resetting them.
I now see the Visual Profiler isn't
what I want. The regular profiler has further breakdowns. Physics2D: 3ms, Script functions (Bullet._process): 3.76ms.
Question: how do you break down the Profiler "Process Time" into individual steps?

Test 6/7: Turning off the bullet's layer does a bit, but deleting the Area2Ds and CollisionShape2Ds completely eliminates the Physics2D profiler entry.
Physics2D is otherwise 3ms of Integrate Forces. This seems like a strange thing, I thought integrate forces was for movement. I suppose Area2D has some extra crap.

Test 8: Disable Bullet's Area2D.Monitoring. Seems to do nothing, probably identical to turning off all Collision masks.

Test 9: Remove the script from each bullet. Instead, the bullet spawner moves and disables the bullets. This should remove the 3.76ms of Bullet._process, and hopefully
not just move it to bullet_spawning._process. This should also remove Physics2D. We'll have to reimplement collisions later.
Actual result: Script's up to 5ms, mostly move_bullets. despawn_bullet is sometimes 3ms as well, so Array.erase() isn't the best.

Test 10: Played with the bullet counts. We're at 2800 for the above experiments. When we hit 5000~ we get exponentially slower, move() goes up to 80ms. I wonder why.
It doesn't look like the slowdown is in despawn_bullet(), it's all a move() problem...
